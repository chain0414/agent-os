基线取修改前 `34f7cbf`，实现后使用相同合成消息、相同 Release 配置、同一 iPhone 17 Pro 模拟器对比。所有探针使用独立 App 标识和离线合成数据，不连接生产账号或真实会话。

本机 Xcode／Simulator SDK 为 26.2，项目发布目标为 26.5。仅验证命令临时覆盖部署目标为 26.2，发布最低版本未修改。收尾检查发现工程仍引用旧团队，按 Wayne 的全局偏好将 Debug／Release 默认团队同步为 `67JNSQB28X`；未改变 Bundle ID，本轮构建关闭签名。以下结果不能替代 iOS 26.5 真机性能或真实远程会话验收。

## 布局性能

每组 100／300／1000 条混合消息，含每隔 30 条出现的百行用户输入、Markdown 标题／列表／代码。挂载真实生产时间线与渲染组件，等待初始解析后执行 12 次 390 ↔ 760 pt 宽度切换，测量同步 `layoutIfNeeded()` 耗时。

常规负载最终对照（包含长回复补优化）：

| 消息数 | 基线中位数／最大值 | 优化后中位数／最大值 |
| --- | --- | --- |
| 100 | 121.39／268.91 ms | 21.11／47.37 ms |
| 300 | 346.82／457.16 ms | 18.94／24.50 ms |
| 1000 | 1184.75／1599.86 ms | 18.50／25.38 ms |

同一进程完成三组后的累计峰值 RSS：基线约 2040.1 MiB，优化后约 307.5 MiB。不是各组独立稳态内存，也未测长期内存泄漏；未控制宿主其他进程负载或热状态。

结果支持：消息分组懒加载与有界预览显著减少此负载下的同步布局成本。它不证明真实物理旋转端到端耗时、真机帧率、电量表现或所有单条大回复的性能。

追加单对 50k 字符用户输入＋50k 字符 Markdown 压力样本，发现基础实现仍有单条回复内部全量布局瓶颈，因此继续将长回复结构块展开到同一根级懒加载布局，正文缓存由消息持有，附件与操作只出现一次。

| 压力样本阶段 | 中位数／最大值 | 峰值 RSS |
| --- | --- | --- |
| 基础实现 `4eeea968` | 375.91／708.79 ms | 503.3 MiB |
| 结构块补优化后 | 81.15／95.80 ms | 368.7 MiB |

采样前断言完整原文已解析且生成 70 个结构块，运行中截图确认视口覆盖长助手回复首段，避免将空白加载状态当成性能提升。70 是解析块总数，不是实际挂载／预取数量。该优化不拆散单个巨大段落、列表、代码块或表格；这些原子结构仍可能昂贵，中段定位、真实动画帧间隔和任意大内容未作全面实测。

复现工具：[探针源码](../../ios/Tests/ConversationPerformanceProbe.swift)、[运行脚本](../../ios/scripts/probe-conversation-performance.py)。原始日志、结果与截图仅保留在本地验收目录，不提交运行产物。基线使用 `--revision 34f7cbf`，优化版省略 revision；两次须指定同一台已启动模拟器及各自输出／DerivedData 目录。

## 正文完整性回归（Build 14）

Wayne 的 Codex／iOS 对照截图指出：iOS 仅剩工具调用，用户和助手正文消失。此前“标签已隐藏”的观察不足以证明对话显示正确，Build 13 的整体验收结论撤回，键盘／性能等专项数据仍按各自范围保留。

只读核查真实会话当前 133 条缓存：33 条用户消息均含非空 instructions，33 条助手消息均含非空 message，其中 32 条与截图中“无新增需求、交付或阻塞……”完全一致，另有 66 条工具记录。原始正文仍在；丢失发生于客户端将已识别指令和静默回执整条过滤的展示规则。

修复 `c57149dd` 保留每条完整已知信封的正文，只去控制字段。DONT_NOTIFY 不再删除聊天正文；分页缺前置指令或缺轮次 ID 不阻止正文显示。工具沿用每轮默认折叠，不跨用户边界合并；原文开关和原始记录保持完整。失败、附件、未知及未完成消息继续原样保留。notice 来自独立 runtime 数据，不能因 idle 或截图中未见就擅自删除。

回归先复现 38 项断言失败，修复后相关 13 项及全部 288 项／36 suites 通过。公司签名 Release Build 14 已覆盖安装，同一 bundle、最低版本 26.5，安装前后 10 个应用数据／偏好文件哈希一致。

Build 14 使用真实账号的「梳理进展并发拆分」执行 1 个对照用例、8 项检查，全部通过：指定目标正确、用户正文前缀可见、助手指定回复完整可见、用户开头低于导航区域、助手完整 frame 位于导航与输入框之间、无控制标签、工具组可见且保持折叠。不是离线样本。除程序断言外，主 Agent 已查看实际 PNG，确认可读的用户输入 →「2 次工具调用」折叠组 → 助手回复顺序；没有展开工具、发送消息、接管或回应 notice。

实际截图单独保留用户正文开头与助手回复两个位置，未用整条 AX value 包含前缀代替屏幕可见。证据：本地 `build14-frame-conversation-user-body.png`、`build14-frame-conversation-assistant-body.png`；用例结果位于 `.local-dev/ios-device-acceptance/results/conversation-bodies-frame-build14/result.json`。这些真实会话图片不提交仓库。两张 runtime 待处理卡片仍保留；本轮仅确认它们不是正文丢失原因，尚未获得权威状态来判定是否过时，未擅自删除。
