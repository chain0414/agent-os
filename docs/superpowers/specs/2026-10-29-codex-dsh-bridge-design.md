## 一、产品目标与日常使用

Wayne 希望在当前 Codex / DeepSeek Harness 对话中叫另一方协助，双方都能发起委派和复核。主要流程是 DSH 讨论方案 → Codex 交叉复核 → 结果返回原 DSH 对话 → 确认方案 → Codex 编码执行。插件应独立安装和运行，不依赖 Agents Anywhere（AA）的 Server、账号、数据库或 Connector；AA 保留为后续可选适配。

以下是设计示例，不是真实调用记录：

1. Wayne 在 DSH 说：“把当前方案交给 Codex review，重点看并发和迁移风险。”
2. DSH 原生插件从真实调用上下文取得来源身份，将需求、方案原文、约束、复核重点和文件范围交给 Codex 的协作会话。
3. Codex 在实际受限权限下复核，完整意见自动回到原 DSH 对话；DSH 逐条说明采纳、拒绝或待验证的理由，并更新方案。双方一致不代表方案已被证明正确。
4. Wayne 说：“按这版方案让 Codex 开始实现。”插件将这条真实用户指令关联到确定的方案版本、工作目录与验收条件，再交接编码。
5. 实际改动、验证证据和未完成事项回到原 DSH 对话。Codex 发起 DSH 委派和复核采用同样流程与约束。

“当前对话”指委派的来源，结果必须返回该来源。接收方默认使用绑定的持久协作会话，没有绑定时创建专用会话；允许明确绑定已有会话，不自动选择最近打开的对话。优先复用接收会话以减少重复上下文；复核与编码不能在同一会话中可靠切换权限时，使用独立受限复核会话并交接完整方案，而不削弱只读要求。

复核结果本身不触发编码；已有明确编码授权时不重复要求确认。用户授权的可执行范围由任务记录限定，复核或实施均不自动包含合并、部署、公开发布或代答权限审批。上述默认保留用户对“确认好方案”的控制，不增加管理面板。

第一版面向同一台 Mac，在原生对话中完成双向协作，界面只展示请求、结果、必要状态及恢复操作。任务、连接日志和验收过程不作为业务说明塞入聊天；版本不兼容、结果过期和权限阻塞需就近明确提示。

## 二、独立交付与接入能力

### 仓库落位与独立交付

推荐技术结构由 Agent 负责选择：本机协作服务 + Codex 插件（Skill / MCP，必要时配宿主 hook）+ DSH 原生插件。服务优先使用 TypeScript / Node 与 SQLite，处理任务、会话绑定、持久回传和恢复；这些均为实现建议，不是已经验证的依赖组合。

| 路线 | 能提供什么 | 取舍 |
| --- | --- | --- |
| 纯 Skill / CLI | 显式委派与脚本执行 | 不能仅靠提示词解决来源身份、异步回传与恢复 |
| 本机服务与两端插件（采用） | 共享任务记录，在原生对话中双向调用 | 必须逐端证明宿主身份与回传通路 |
| AA Server / Connector 中心调度 | 复用更多已有运行能力 | 引入 AA 依赖，仅作为可选适配，不作为默认安装要求 |

源码留在当前仓库，新增与 `connector/`、`dsh-bridge-next/` 同级的 `agent-collab/` 子项目，建议路径 `/Users/wayne/mywork/dev/agents/Agents-Anywhere/agent-collab`。目录名表示协作职责；第一版仍只做已确定的 Codex / DSH 流程，不扩展成通用 Agent 平台。以下是建议布局，尚未创建：

```text
Agents-Anywhere/
├── agent-collab/
│   ├── AGENTS.md
│   ├── package.json          # 仅本子项目的 workspace 与检查命令
│   ├── contracts/            # 本机协作协议、fixtures 与版本
│   ├── packages/
│   │   ├── service/          # 协作核心、本机服务、MCP、Codex 接入
│   │   └── dsh-plugin/       # DSH 原生工具、来源身份与回传适配
│   ├── plugins/codex/        # Codex 安装描述、Skill 及必要 hook
│   └── tests/installation/   # 仅用发布产物验证独立安装
├── connector/                # 后续可选 AA 接入所在层
├── dsh-bridge-next/          # 现有 AA 远程控制插件
├── contracts/                # AA 跨端契约
└── docs/
```

`agent-collab/` 自己安装依赖、构建、检查和打包，沿用仓库的 Node / TypeScript / Yarn 使用方式；不将全仓改成一个 Node workspace，不引入根目录统一构建，不提交 lockfile。服务、DSH npm 插件和 Codex 插件是不同安装入口，按宿主要求分别产出；DSH 插件仅依赖明确的发布包／本机服务接口，Codex 的清单和启动器也只引用完整分发产物。独立用户无需克隆 AA 仓库、安装 Connector 或配置 Server。

依赖关系为“两端入口 → 本机协作服务 → Runtime 接入”，协作核心只处理任务与能力接口。DSH 接入在原生插件进程中调用已有宿主控制器，通过本机协议与服务通信；不再启动一套 DSH Agent。Codex 接入使用已验证的 app-server 或 owner 路径。两端连接通过同一受认证的发现机制找到服务；多入口启动时只允许一个服务实例拥有该数据目录和工作区执行权，不能各自启动互不知情的调度器。

AA 接入位于 Connector 的集成层：Connector 通过版本化本机 API 使用协作服务，需要远程展示时再经现有 Server / Timeline 边界投影。协作服务不反向依赖 Connector 内部模块，也不同时引入另一条由 AA 管理相同任务的调度链。协作服务是 Runtime 之上的任务协调者，不注册为与 Codex / DSH 并列的新 Runtime；Runtime 继续持有原生会话、文件操作与审批，协作服务只拥有任务、绑定、回传及写调度状态，AA 拥有账号与远程视图。

与现有 DSH 远程控制插件同时安装时，使用独立服务名、配置、socket 和任务存储，不抢占 `agentsAnywhereRuntime` 或 Connector rendezvous；共享同一宿主的原生会话控制器。直接操作的并发服从 Runtime owner／轮次规则，不能因为两个插件位于同仓就假定共享了任务写锁。

复用源码前核对许可证及分发条件。优先复用协议、fixtures、行为测试和小模块；确认有两个实际消费者时，再将通用接入代码提取为可独立安装的底层包，让旧插件和新组件依赖同一包。新组件不得通过 `../../connector` 或 `../../dsh-bridge-next/src` 运行时导入，也不将整个 Connector 复制进发布包。现有 Codex 接入主要为 Python，不能视为可直接导入 TypeScript 的库；若跨语言提取成本高，先复用契约和一致性测试，后续单独决定客户端库的语言与维护边界。

实施时同步补齐仓库治理，不将独立性作为默认违反现有规则的理由：

- 根 `AGENTS.md`、开发指南登记新组件及检查命令；在 `docs/versioning.md` 明确可独立发布的协作扩展与 AA 各端的适用范围。新扩展建议采用自身 SemVer，并记录宿主兼容矩阵，不机械跟随 AA 的 `2.x`；在规则更新前不自行制造版本例外。
- 独立协作协议主源在 `agent-collab/contracts/`，先写 schema / fixtures 后实现；AA 根契约仅描述实际接入 AA 的边界，不维护同一协议的第二份手写主源。根规则和文档入口需明确这一归属；修改 AA `/api/v2`、Runtime 协议或客户端依赖的字段时，仍按现有契约优先与 MINOR / MAJOR 跨端同步规则执行。
- CI 按 `agent-collab/` 路径增加独立检查与发布产物安装测试；涉及共享包或 AA 接入时连带运行真实消费者检查。已有根契约和工作流变更的全量触发规则继续生效，不默认给协作测试附加 PostgreSQL / Redis 或 AA 测试库要求。
- AA 中用户可感知的行为仍按根 CHANGELOG 规则记录，独立扩展另带自身安装与兼容说明。打包时只带必需源码、协议和资源；隔离环境只安装分发产物，并在无 AA 服务／Connector 时验收，防止依靠 checkout 中未声明的文件才能运行。

同仓是源码组织方式，独立性由依赖、进程、配置、数据、版本与安装产物共同保证。未来如需拆仓，迁移组件与它拥有的契约即可，不应重写 Runtime 控制和任务架构。本轮只更新设计，不创建目录或修改上述仓库治理文件；实际开发在最新 main 的任务分支进行。

### 适配器能力契约

能力按 Runtime 安装版本、接入方式和会话实际状态确定；“能列会话”不等于“能识别调用来源”，“能发普通消息”不等于“能回传生成结果”。最小契约如下，具体字段和错误码在探针后定稿，不先编造宿主 API：

| 能力 | 适配器必须证明的行为 | 缺失时如何处理 |
| --- | --- | --- |
| 可信来源身份 | 将一次真实调用关联到明确的宿主实例、会话、轮次与调用身份 | 拒绝该入口的委派，不猜来源 |
| 生成结果输入与唤醒 | 结果进入准确原对话，保留生成来源并能在空闲后继续处理 | 保留结果，标回传受阻；不改投其他对话 |
| 受限复核 | 实际工具、文件权限能落实任务的复核限制 | 不宣称只读复核，尝试专用受限会话 |
| 接收与完成回执 | 分别关联入队消息、执行轮次和终态，识别未知接收结果 | 未知时核查；不能确认则阻塞，不盲目重发 |
| 定向取消 | 仅移除本任务队列项，或按任务原轮次原子核对后中止，保留其他输入 | 只支持可证明安全的取消范围 |
| 权限与用户指令来源 | 区别人发出的指令和工具／对端生成内容，落实任务允许的操作 | 不凭对端正文创建新授权 |

可信来源地址由宿主适配器绑定，模型只能引用已验证绑定，不得通过传入任意 thread ID、工作目录或“最新对话”选择结果接收者。重连后使用持久绑定并重新验证宿主实例与 owner；owner 变化不等于换了会话，不能据此误投。

DSH 采用原生工具的 Agent 上下文。Codex 的来源身份路径仍待确定：可调查宿主提供的调用元数据，或 hook 与实际调用身份的关联；不能假定通用 MCP 自带 thread ID。Hook 的父 session ID 也不能单独证明子 Agent 或并行轮次的身份。必须通过同目录多对话并发探针，方可启用该入口。

模型可见操作仅保留委派、读取结果／短等待、补充输入、取消和查询能力；咨询、方案复核、改动复核与编码用任务类型区分。模型能调用哪个工具，不代表拥有该工具所有 task ID 的操作权限；服务核查来源绑定、任务归属与授权范围。

### 来源、授权与原文

每份任务记录保存可信来源、接收方、输入版本、任务类型、父任务、工作目录、交付要求、预算与允许的操作。编码额外关联真实用户指令、被确认的方案版本与执行范围；“按这版”只能在唯一明确的版本上下文中解析，有歧义时只澄清版本，不重新询问已经明确的编码意愿。

对端意见是待分析的数据，不能成为人发出的新命令。同步等待时通过原工具结果返回；异步时使用宿主支持的生成结果输入，并保存任务、结果版本及来源。不能直接复用把输入标为 `user` 的发送接口，也不能仅靠正文前缀、自定义 source 字段或网络客户端认证宣称解决了授权边界。需要同时检查原生历史、模型可见内容与服务允许的后续动作。

回传保留模型原文、证据定位与未验证假设；摘要单列并注明。大结果保存完整本地文件，提供可定位入口，不静默截断改变判断的限定条件。来源身份由适配器记录，模型不能自行声明身份。状态、任务和凭据文件仅当前用户可访问；凭据不得进入任务正文、命令行参数或日志。

## 三、任务执行、异步回传与双向等待

### 生命周期与投递

服务先持久接收任务再返回任务 ID。执行状态与投递状态分别记录：本地排队、Runtime 接收待确认、已接收／执行中、等待用户处理和执行终态；结果另记录待投递、投递待确认与已投递。“执行完成”不能直接显示成“已回传”。

Runtime 接收时保存消息 ID，开始执行时关联该任务的原轮次／generation；成功、失败、中断和需要人处理分别记录，不能把一段 assistant 文本或开始轮次的 ACK 当作成功完成。请求超时且接收结果未知时，先通过 Runtime 消息／事件与稳定请求标识核查。无法核查时保持未知并阻止自动重发，不承诺底层天然支持 exactly-once。

短等待只是读取结果的便利入口。服务按任务和结果版本原子决定由仍有效的等待调用接收，或转入持久回传队列；读取返回“已受理”不算消费结果。调用断开、宿主接收结果未知时保留投递记录并核查回执，不同时安排两个自动通知。用户主动再次读取结果可以返回同一原文，但不能因此重复启动后续处理。

异步回传在原对话的安全调度边界提交，目标归档、owner 不可达或生成结果通路不可用时保留结果并显示重试／重新绑定入口；重新绑定需要明确意图，不静默改投其他会话。投递不能抢占正在处理的用户轮次。用户打开对方原生客户端查看或继续会话的体验，需单独验收，不能由“磁盘存在会话”推断。

### 繁忙与互等

繁忙的目标会话排队，不抢占、不另开 app-server 强行恢复被占用会话。服务维护实际阻塞的“来源轮次等待目标会话”关系，同时检查父任务链和跨独立根任务的等待环。

目标为 busy / queued 时，来源工具立即返回任务 ID 和当前状态；来源不继续循环短等待，应结束该轮次或处理不依赖结果的工作，后续由异步结果恢复。这是 Skill 与宿主调度共同落实的规则，不能只靠提示词保证；服务检测到等待环时，退回可解除等待的一方为异步模式，并验证来源已释放。若宿主不能释放或安全恢复，任务报告受阻，不无限重试。

每个任务有总截止时间及自动往返预算，不只限制单次工具等待。自动追问默认最多两轮，可按任务调整；对端提出“再让另一个 Agent 做某事”仍需在原任务已授权范围内，否则仅回传建议。原生审批留在原 Runtime，服务不得自动批准来解除等待。

### 取消的准确范围

取消只作用于当前来源有权操作、且插件拥有的任务。未交给 Runtime 的本地排队任务可直接取消；已接收但尚未开始的任务，仅在适配器能定向移除相应消息并核查结果时取消。

执行中的取消必须携带任务已保存的原轮次／generation，由 owner 原子比较后中止，不能重新读取“此刻活动轮次”替代原轮次。取消不得清空其他队列输入。任务已完成、其他轮次已开始或归属不匹配时，返回已结束／不匹配，不停止后续工作。

适配器只有会话级停止、或无法保留其他队列消息时，不能将其暴露为安全任务取消；提示“已进入执行，当前接入不支持安全停止”，继续跟踪真实结果。截止时间到达同样不意味着执行已停止：无法安全中止时记录停止未确认，不释放仍占用的写执行权，不重新启动替代任务。

## 四、代码一致性、权限与 token

### 工作区写入与复核版本

会话排队与工作区写入互斥分别处理。第一版将插件管理的编码任务按规范化工作树身份串行调度；路径先解析真实路径，同一工作树中的子目录共用执行权，非 Git 目录使用明确的规范化工作目录。实现阶段核对别名和目录重叠；不能仅比较用户输入的路径字符串。

写任务的执行权由服务持久记录，持有至 Runtime 确认真正结束，或有证据证明执行者已退出。服务重启后先核查仍活跃的任务，再分配新任务，不能因超时、取消请求或连接中断就假定旧任务停止。未来需要并行时给任务隔离 worktree，并明确独立的集成与验收步骤。

插件互斥只能约束插件调度的任务，挡不住编辑器或原生对话直接写文件。每次编码记录起始 Git 基线、已有未提交改动与相关文件摘要，不覆盖或清理用户已有修改。任务开始前、复核取证时及交付时检查外部修改；基线变化时重新核对差异与结果归属，发生冲突则暂停相关写操作并说明。

方案摘要只标识方案原文，不标识代码。方案复核关联方案版本，改动复核另关联确定的代码快照／差异基线；已有未提交文件也纳入快照。复核期间或复核后相关文件变化，旧结果标记过期，不声称新代码已被复核。编码交接包含完整方案、已解决与未解决的分歧、文件范围和验收条件。

### 执行权限与上下文

任务工作目录只是上下文，不是文件系统权限沙箱。只读复核要由实际可用的权限配置和工具能力落实；既有桌面对话可能继承宽权限，不能仅传“review”提示词声称降权。优先验证同一会话在复核与编码间切换权限；不可靠时分为受限复核会话与编码会话，并保留交接原文、版本和证据链。

第一次交接要让对方独立理解需求、约束、方案和证据；后续只发送有版本关联的变化，对方可请求缺失背景。会话压缩、重建或绑定变化后，先确认接收方持有的版本，再恢复增量交接；不能因为复用了一个 thread ID 就假定全部上下文仍在。

### 预算与用量

分别记录真实任务用量、上下文空间和可读取的账号额度；缺失标未知，估算单独标注。第一版优先控制交接输入、输出长度、自动往返次数、任务总时间和并发，只有 Runtime 原生支持并经过验证时才宣称执行中 token 限额。

预算跨本次委派的后续追问累计，不能每次短等待或重试都重置。停止投递、达到 deadline 或停止等待都不等于停止模型计费，必须如实记录尚在执行的状态。插件不承诺账号额度可转移，也不将结束后的用量通知当作硬预算控制。

## 五、证据、实施验证与本轮交付

### 已有证据及限制

以下是此前源码和官方文档核查所得，不是安装版本的运行证明：

- AA 的 `dsh-runtime/router.ts`、`native.ts` 已有创建会话、开始轮次、状态／快照读取与中断等能力；`connection.ts` 依赖 Connector rendezvous、AA Sync / Logs，不能原样包装后称为独立插件。
- 本机 DSH 原生工具的 `ToolExecutionInput.agent` 有 loop 提供的身份；现有 `sessionController.prompt` 把输入来源设为 `user`，其会话级取消默认可能清空 inbox。因此来源绑定、异步生成结果及定向取消需要不同适配路径。
- AA Codex SDK 与 IPC 是两条控制通路。桌面既有 owner 使用 `thread-follower-*` 请求；恢复存档不是加入任意活跃窗口，已知 owner 也不能反向证明 MCP 来源身份。
- [官方 App Server 文档](https://learn.chatgpt.com/docs/app-server) 描述 thread / turn、独立 `toolOutput` 输入和用量事件；仍需确认安装版本及桌面 owner 路径兼容性。[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks) 提供身份候选线索，不构成已选定实现。[官方 Skill 文档](https://developers.openai.com/plugins/concepts/skills) 区分工作流和 MCP 动作。

原始源码路径、失败场景和各项推导见[复审报告](2026-10-29-codex-dsh-bridge-review.md)。复审中的旧设计行号链接到 v1 快照；源码路径是本机证据，不作为插件运行依赖。

### 实施顺序与验收

先完成真实接入验证，再扩展完整服务。探针可使用临时最小宿主连接和固定无敏感请求，不需要先实现完整队列；探针成功只证明对应接入能力，不代替真实模型协作验收。

| 阶段 | 具体场景与判断标准 |
| --- | --- |
| A1：来源绑定 | 同目录两个 Codex 对话并发调用、结果各回原对话；DSH 同样验证；覆盖重连、owner 变化和子 Agent，不靠模型任意填写 ID |
| A2：异步结果 | 两端原轮次结束后仍收到结果；检查原生历史、模型可见内容和来源标记；复核正文要求直接编码时，未获人授权不得开始编码 |
| A3：权限与取消 | 验证受限复核及授权后编码；取消与任务完成／用户新轮次交错，不误停其他轮次、不删除其他队列输入；不支持的取消准确禁用 |
| B：调度与恢复 | 假适配器验证同工作树写互斥、重启后的执行权恢复、跨根等待环、结果消费与投递竞态、接收未知、截止后仍运行、版本过期和外部修改 |
| C：真实主流程 | 当前 DSH → Codex 真实方案复核 → 原 DSH 处理意见 → 明确版本后 Codex 编码 → 返回真实改动与验证证据；另完成 Codex → DSH 反向流程 |
| D：独立安装 | 从发布包／插件 bundle 在隔离目录安装，禁止引用源码 checkout；无 AA Server、账号、Connector 或 AA 数据库时完成核心能力；两端同时启动仍共用一个服务；与旧 DSH 远程控制插件并装不抢占彼此入口，并验证原生客户端查看／继续协作会话；记录实际支持版本，再考虑 AA 适配 |

A1、A2 是对应方向可启用委派的前提。A3 中安全取消可以按能力缺失处理，但不能默默弱化来源身份、回传或受限复核来完成演示。任一方向尚未通过时，不宣称已交付双向插件；如需改变已确认的产品体验，先报告证据和影响。

真实端到端记录区分用户输入、模型原文、Agent 分析和人工判断；固定传输请求与模拟适配器结果明确标注。Headless 通过不等于原生对话可用，字段存在不等于证据支持复核结论。
